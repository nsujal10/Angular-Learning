Exercise 48

Component State vs. Service Architecture

Anti-Pattern (Common Mistake)

State trapped in EmployeeDashboard

Putting all raw data and manipulation logic directly inside the component class:

// ❌ Tightly Coupled
@Component(...)
export class EmployeeDashboard {
  employees = [ ...raw data ];
}
  • Difficult to Test: Cannot unit-test data operations without instantiating the entire UI component DOM.
  • Zero Reusability: Other components (e.g. Org Chart, Payroll, Reports) cannot access this employee list.
  • Violates SRP: The component is responsible for UI presentation, layout, filter logic, AND persistence.
Best Practice (Current Refactor)

EmployeeDashboard ➔ EmployeeService

Injecting a singleton service providing a single source of truth:

// ✅ Decoupled & Injectable
private employeeService = inject(EmployeeService);
employees = this.employeeService.getEmployees();
  • Easy to Test: Can mock EmployeeService seamlessly in isolated component unit tests.
  • High Reusability: Any feature across the application injects the exact same service.
  • Future-Proof: Swapping mock arrays with HttpClient HTTP calls requires zero changes to UI templates.
